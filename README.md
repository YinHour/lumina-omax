## 为什么需要知涌

石油化工研发团队的问题，往往不是“不会问 AI”，而是研发活动本身缺少一套可被 AI 承接的结构化方法。

很多企业已经积累了大量实验报告、产品说明书、评价记录、原始数据表、现场反馈和外部文献。但这些资料常常分散在不同项目、不同人员和不同格式里：

- 同一产品代号可能对应多个配方版本，现场表现和实验结果难以对齐。
- 历史报告以 PDF、Word、Excel、旧版 Office 和图片为主，难以统一复用。
- 实验数据更偏应用结果，缺少原料批次、工艺参数、理化指标、测试条件和失败原因等关键字段。
- 研发人员容易直接问“下一步怎么做”，把决策外包给 AI，而不是让 AI 参与一条清晰的科研链路。
- 管理层关心成本、现场风险、交付周期和项目复用，但研发资料通常停留在一次性报告。

Lumiton·Omax | 知涌的目标，是把这些分散材料变成一套可复制的研发操作系统：先组织证据，再生成假设，再设计实验，再复盘沉淀，最后形成管理视图和下一轮研发动作。

## 产品定位

知涌不是一个只回答问题的聊天工具，而是面向石油化工研发场景的知识工作台。

它帮助团队围绕“产品代号 - 配方版本 - 原料批次 - 水泥批次 - 工况条件 - 性能结果 - 失败原因 - 下一轮实验”建立闭环，让 AI 服务于研发过程，而不是替代研发判断。

在油井水泥外加剂研发中，知涌尤其适合从一个明确试点开始，例如“油井水泥用降失水剂”：

- 汇总 HX-12、HX-14、HX-16 等历史产品资料。
- 梳理小试样、中试样、生产样和现场样之间的关系。
- 对齐不同水泥批次、水质条件、温度压力和性能结果。
- 总结降失水、流变、稠化、强度、稳定性等关键指标的证据。
- 生成可验证的机理假设和最小实验矩阵。
- 复盘失败案例，沉淀下一轮实验问题和项目 Gate 状态。

这套方法跑通后，可以迁移到缓凝剂、分散剂、减阻剂、冲洗剂、隔离剂、堵漏剂、膨胀剂等更多产品线。

## 研发操作系统闭环

### 1. 项目立题与边界定义

知涌引导研发人员先定义问题，而不是直接向 AI 许愿。

一个项目开始前，应明确：

- 服务哪个产品线和应用场景。
- 目标区块、温度、压力、水泥厂家/批次、水质条件。
- 当前不达标指标和具体失败表现。
- 成功判据、成本约束、工艺约束和交付周期。
- 进入实验设计前还缺哪些数据。

系统可以根据已上传资料生成“项目问题定义卡”，把宽泛问题改写成可实验验证的问题。

### 2. 资料分层与证据地图

知涌把“资料堆叠”整理为“证据体系”。

一个试点项目可以拆成多个主题笔记本：

- 产品说明与技术指标。
- 历史研发报告。
- 实验记录与原始数据。
- 中试、生产样与现场反馈。
- 水泥批次、水质与工况条件。
- 外部文献与竞品资料。

系统可以识别每份资料的证据类型、关键指标、缺失字段和证据强度，建立“指标 - 实验 - 结论 - 文件来源”的证据地图。

### 3. 产品-配方-场景映射

知涌帮助团队解决“同一产品代号对应不同配方，现场表现对不上”的核心管理问题。

建议至少建立这些字段：

- 产品代号：如 HX-12L、HX-14L、HX-16L、HX-16S。
- 配方版本：小试、中试、生产样、现场样。
- 功能类型：无缓凝、分散性、高强度、耐温抗盐等。
- 原料批次、供应商、水泥厂家、水泥批次和水质条件。
- 温度、压力、密度、盐度等工况条件。
- 降失水、流变、稠化、强度、稳定性等关键性能指标。
- 实验结果、现场结果和异常现象。

系统可以从历史报告中抽取产品代号和配方版本线索，发现同名产品下的配方差异，并识别水泥批次或水质变化导致性能波动的案例。

### 4. 机理假设生成

知涌不鼓励直接给“最终配方”，而是先生成可验证的机理假设。

例如在降失水剂研发中，系统可以帮助分析：

- 哪些理化指标可能影响降失水性能。
- 哪些因素可能影响高温稳定性。
- 哪些机制可能导致包芯、倒挂、稠化异常、强度不足。
- 水泥批次差异可能通过哪些机制影响结果。

每个假设都应包含已有证据、反证风险、需要补测的理化指标、推荐验证实验，以及假设成立后的下一轮配方调整方向。

### 5. 实验矩阵设计

知涌把 AI 建议转成可执行实验，而不是灵感列表。

每轮实验都应明确：

- 固定变量和待考察变量。
- 对照组。
- 测试指标和通过标准。
- 失败判据。
- 是否进入中试或现场验证的 Gate。

系统可以帮助生成最小实验矩阵，控制实验数量，减少无效组合，并解释为什么这样设计。

### 6. 实验后复盘

知涌让每次实验都沉淀为资产，而不是只留下一个报告文件。

实验结束后，系统可以帮助研发人员回答：

- 原假设是什么。
- 哪些数据支持假设。
- 哪些数据与假设冲突。
- 失败更可能来自配方、工艺、原料、水泥批次、测试条件还是现场条件。
- 下一轮只应该验证哪 1-2 个问题。
- 这次实验应该沉淀成什么知识规则。

复盘结果可以保存为笔记，成为下一轮研发的证据和起点。

### 7. 项目 Gate 与管理层摘要

知涌把技术过程转成管理层可理解的项目视图。

每个研发项目可以设置 4 个 Gate：

- Gate 1：问题定义完成，关键资料齐备。
- Gate 2：机理假设明确，实验矩阵通过评审。
- Gate 3：小试结果达标，成本与工艺风险可控。
- Gate 4：中试或现场验证通过，可进入产品化或客户应用。

系统可以生成每周项目状态摘要，标记当前 Gate、已达成证据、未解决风险、对成本和交付周期的影响，以及是否建议继续推进、补实验、暂停或调整方向。

## 面向三类角色的价值

### 管理层：把研发改善翻译成经营结果

知涌帮助管理层看到研发活动如何影响成本、风险和交付：

- 核心产品成本是否有下降空间。
- 现场技术问题是否有减少趋势。
- 关键项目是否按时推进。
- 哪些知识可以复用到其他产品线。
- 哪些风险需要管理层协调资源。

系统不只给技术建议，还会把建议对成本、现场风险和周期的影响显式呈现。

### 研发负责人：从经验试错转向机理与预测

知涌帮助研发负责人补齐“机理假设 - 实验验证 - 规律沉淀”的中间层：

- 区分已有证据、合理推断和需要补充验证的内容。
- 从历史实验中总结“配方 - 条件 - 性能”的规律。
- 引导团队补齐实验元数据，而不是只上传最终报告。
- 为降失水剂、缓凝剂、分散剂等产品更新建立可复用方法。

### 一线研发人员：把不可复用经验变成结构化资产

知涌帮助一线研发人员把日常经验变成可复盘、可查询、可传承的研发资产：

- 固定记录失败案例。
- 建立产品代号、配方版本、应用区块、水泥批次之间的映射。
- 把每次问答、实验复盘和改进方向保存为项目知识。
- 避免在高温高压测试、中试放大和现场应用中重复试错。

## 核心能力

### 多格式研发资料入库

- 支持 PDF、Word、Excel、PowerPoint、网页、音频、视频等来源类型。
- 支持 `.doc`、`.xls` 等旧版 Office 历史资料继续进入知识库。
- Excel 表格会清理整列空白列，并尽量保持表格结构可读。
- 来源详情页适合阅读长文档、长表格和长引用。
- 原始文件名会被保留，便于追溯和重复检查。

### 证据问答与全局检索

- 支持笔记本内对话、来源对话和全局 Ask。
- 全局 Ask 展示来源总数、可检索来源、本次命中来源。
- 回答历史可回看问题、答案和覆盖统计。
- 回答后生成下一步建议问题，引导用户继续沿研发链路追问。
- 长耗时问答显示阶段提示，避免用户误以为系统无响应。

### 研发知识组织

- 用笔记本组织产品线、项目、实验记录、现场反馈和外部文献。
- 用聚合笔记本汇总一个试点项目的多个资料维度。
- 支持来源搜索、分页、筛选、全选和来源数量上限。
- 支持“只看我的”，适合多人试用时快速找到自己的研发工作区。
- 支持将问答结果、复盘结论和管理摘要保存为笔记。

### 多人协作与内网部署

- 支持多用户账号、注册审批、角色区分和管理员设置。
- 支持上传者、创建者和更新时间追溯。
- 适合企业内网源码部署，浏览器通过前端 `/api` 代理访问后端。
- API、worker、前端和数据库日志分别保存，便于排查长耗时任务和模型调用问题。

## 推荐试点路径

第一阶段建议不要同时铺开所有产品线，而是选择一个边界清晰、资料较多、管理层关注度高的试点。

推荐试点：油井水泥用降失水剂。

建议 1 个月内完成：

- 建立“降失水剂研发方法试点”聚合笔记本。
- 整理至少 30 份历史资料为证据地图。
- 建立产品代号与配方版本初始映射表。
- 完成 3 次结构化问答并沉淀为笔记。
- 形成 1 份下一轮实验矩阵。

建议 3 个月内完成：

- 形成降失水剂实验记录最小数据库。
- 识别 3-5 条可复用研发规则。
- 减少重复试错实验组合。
- 输出至少 1 个可进入中试或现场验证的方案。
- 形成可迁移到缓凝剂、减阻剂等产品线的研发流程模板。

## 最小数据模板

为了让 AI 真正参与研发过程，上传报告之外还需要补充最小结构化字段。

实验记录建议至少包括：

- 项目名称、产品代号、配方版本、功能类型。
- 原料与批次、合成工艺参数、理化指标。
- 水泥条件、水质条件、工况条件。
- 测试指标、结果判定、异常现象。
- 失败原因假设和下一步动作。

现场反馈建议至少包括：

- 客户、区块、井号和工况。
- 使用产品、配方版本、生产批次。
- 水泥与水质条件。
- 施工表现、固井质量、客户反馈。
- 研发判断和后续动作。

这些字段不要求一开始完整，但必须逐步沉淀。只有数据结构稳定，AI 才能从“回答问题”升级为“支持预测和决策”。

## 部署与使用

### 运行环境

- Docker，用于启动 SurrealDB。
- Python / `uv`，用于 API 和后台 worker。
- Node.js / npm，用于前端。
- LibreOffice，用于旧版 Office 和演示文稿转换。
- 可用的 AI 模型凭据，或企业内网中的 OpenAI-compatible / Ollama 服务。

### 本地启动

准备 `.env` 后，启动完整服务：

```bash
make start-all
```

默认端口：

| 服务 | 地址 |
| --- | --- |
| 前端 | `http://localhost:3001` |
| API | `http://localhost:5056` |
| API 文档 | `http://localhost:5056/docs` |
| SurrealDB | `127.0.0.1:8001` |

停止服务：

```bash
make stop-all
```

查看状态：

```bash
make status
```

局域网访问时，用户浏览器应访问前端地址，例如 `http://<部署机器IP>:3001/`。浏览器侧请求走相对路径 `/api`，由前端代理到后端。

## 常用开发命令

```bash
# 前端 lint、测试和生产构建
make codex-frontend-check

# 后端 ruff 和 pytest
make codex-backend-check

# 快速检查 diff 空白问题
make codex-quick-check

# 仅启动数据库
make database

# 仅启动 API
make api

# 仅启动 worker
make worker-start
```

## 后续方向

知涌后续将继续围绕石油化工研发操作系统完善：

- 图片识别从“描述画面”升级为“读取关键数值、判断是否合格、指出异常”。
