# 01-基于通过内网IP访问系统的多用户登录访问系统的实现

## 原始需求描述

接下来的需求是在现有的多用户机制和支持内网不同IP使用的基础上，实现企业内部不同用户的账号密码登录功能，在源列表中显示上传者名称。在数据的隔离上保持当前的状况。同时需要考虑用户登录页面的设计。还有用户的注册功能。先谈谈你对该需求的理解。

## 需求分析

## 现状分析

### 当前认证机制
- **`api/auth.py`**：`PasswordAuthMiddleware` 中间件，单一全局密码（环境变量 `OPEN_NOTEBOOK_PASSWORD`），所有用户共享同一密码
- **前端** `auth-store.ts`：将密码存入 localStorage，所有 API 请求带 `Bearer {password}` 
- **登录页** `LoginForm.tsx`：已存在但只输入密码，无用户名概念

### 用户身份现状
- **无 User 表**：数据库中没有用户/账号表，migration 已到 24
- **Notebook.creator_name**（migration 16）：自由文本字段，仅装饰性展示（NotebookCard 底部），不链接到任何账号
- **Source 模型**：无 uploader/creator 字段，只有 `origin_notebook_id`（首个笔记本）

### 数据隔离现状
- Notebook 级别的密码保护：访问加密笔记本需输入密码
- Notebook 是核心隔离单元：不同用户通过不同笔记本区隔数据

## 需求理解

要做一个**企业内网多用户账号系统**，核心变更如下：

| 维度 | 现状 | 目标 |
|------|------|------|
| 认证方式 | 单一全局密码 | 用户名 + 密码，每人独立账号 |
| 用户模型 | 无（仅 Notebook 上自由文本 `creator_name`） | 新增 `User` 表，存储用户名/密码哈希 |
| Source 归属 | 无上传者记录 | Source 新增 `uploaded_by` 关联 User，源列表展示上传者 |
| 数据隔离 | 笔记本密码 | **保持不变**（不引入按用户隔离数据的逻辑） |
| 登录页 | 仅密码输入 | 用户名 + 密码双字段，重新设计 UI |
| 注册 | 无 | 新增注册页面/接口 |

## 关键设计决策点

1. **认证令牌**：从"明文密码即令牌"升级为 **JWT**（含 user_id + username，过期可控），前后端均需改造
2. **User 表字段**：`username`（登录用）、`password_hash`（bcrypt）、`display_name`（展示用）、`created_at`
3. **Source 关联**：Source 表加 `uploaded_by` 字段，记录上传用户 ID，上传时从 JWT 中获取当前用户
4. **数据隔离不动**：用户登录后可访问所有笔记本（取决于笔记本质密码，而非用户），保持当前松耦合
5. **注册策略**：企业内网场景，开放注册（无需邀请码），但可加 `ALLOW_REGISTRATION` 环境变量控制开关
6. **向后兼容**：现有数据（无 uploader 的 source）显示为"未知用户"或空，不破坏已有功能

## JWT secret 是用现有 OPEN_NOTEBOOK_ENCRYPTION_KEY 还是新增独立环境变量？

两个选项的核心区别：

### 技术层面

| | 复用 `OPEN_NOTEBOOK_ENCRYPTION_KEY` | 新增独立变量（如 `AUTH_JWT_SECRET`） |
|---|---|---|
| **用途** | 一把密钥两用：Fernet 加密（API Key 存储）+ JWT 签名（用户登录令牌） | 各司其职，互不干扰 |
| **格式约束** | Fernet 要求 32 字节 URL-safe base64；JWT HS256 仅需足够长的随机串。复用意味着 JWT 被迫遵守 Fernet 的格式 | 各自独立，无格式耦合 |
| **密钥轮换** | 换密钥时，Fernet 加密的所有 Credential 密文 + 所有已签发的 JWT 全部失效 | 可独立轮换：例如 JWT 泄露后只换 JWT secret，不影响已存储的加密 API Key |
| **泄露影响面** | 一把泄露，API Key 明文 + JWT 伪造一起爆 | 单向隔离，降低爆炸半径 |

### 语义层面

- `OPEN_NOTEBOOK_ENCRYPTION_KEY`：守护的是**静态数据**（存库里的加密凭据），属于"数据安全"
- `AUTH_JWT_SECRET`：守护的是**动态会话**（用户登录态签名），属于"身份认证"

两者是不同的安全域：前者是"数据库里的秘密保护"，后者是"用户是谁的签名证明"。混用虽在工程上可行，但在安全审计和运维实践中不推荐。

**建议**：新增独立变量，例如 `AUTH_JWT_SECRET`，部署时要求在生产环境单独生成一个强随机值。同时 `OPEN_NOTEBOOK_ENCRYPTION_KEY` 保持现状不改。
